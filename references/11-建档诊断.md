## 一、这次诊断要交付什么

建档不是把空模板填满，而是把「我想做 IP，但不知道做什么」诊断成一个能开始验证的方向。首次合理交付是 **v0.1 暂定档案**，不是「最终定位」。

诊断的硬原则：

- 从真实经历、反复被求助的问题和可验证结果出发，不先问「你的定位是什么」。
- 每轮只问一个核心问题；一个问题里不塞多个需要分别回答的小问。
- 用户答不出时，基于已知事实提 2—3 个候选方向，逐个说明适合什么、放弃什么、如何验证。
- 每个模块结束先给「当前理解 / 矛盾 / 未知」，让用户纠偏，再进下一个模块。
- 有了最低可执行假设就停止无限追问，进入第一批内容和判断契约，让数据继续回答。

「想涨粉」是结果愿望，「帮助普通人」是空人群，「真诚分享」是表达态度。三者都不能单独作为正式定位。

## 二、状态与断点

档案 frontmatter 使用两个字段：

```yaml
onboarding_status: in_progress
onboarding_step: goal
```

`onboarding_status` 只能是：

- `in_progress`：访谈已开始，核心字段可以不完整，不得当作可直接使用的完整档案。
- `provisional`：六模块达到完成门槛，用户看过完整草案并一次明确确认；可进入第一批内容验证。
- `confirmed`：核心方向经后续内容、用户或业务证据支持，并经用户确认晋级为稳定底座。首次访谈默认不直接写此状态。

状态晋级只有两条：**访谈完成并确认：`in_progress → provisional`；后续证据支持并确认：`provisional → confirmed`**。不得跳级，也不得把第二条错写成“数据验证后进入 provisional”。

`onboarding_step` 只能是 `goal | evidence | audience | value | business | execution`。访谈中断时，先把已完成的结论按「事实 / 假设 / 未知 / 依据 / 验证」写入档案，再把 `onboarding_status` 留在 `in_progress`，`onboarding_step` 指向下一个未完成模块。下次只续这个断点，不重问已确认事实。

`provisional` 或 `confirmed` 档案若缺首次建档核心字段，必须退回针对性补问，不得因为文件存在就判定「已有完整档案」。

## 三、访谈的六个模块

以下是访谈树，不是一次性问卷。每轮只选当前最能提高决策质量的一个问题。

### 1. 目标 `goal`

**默认首问：** 最近发生了什么，让你现在开始做 IP？

默认首问只用于用户尚未给出目标信号的情况。用户原话已经包含「只想涨粉」、明确业务结果或多目标冲突时，直接进入对应分支，不为走题序而重问默认首问：

顺着回答追问：

- 若同时想要涨粉、变现、影响力或职业转型：「90 天只能优先拿到一个结果，哪个结果一旦完成，其它事更容易？」
- 若只说「想涨粉」：本轮只问「粉丝增加后，你真正希望发生的业务或人生变化是什么？」；不要先重问为什么现在，也不要同时追加用户、内容或平台问题。
- 若目标冲突：把冲突说透，要求选一个主目标，其余降级为约束或不追目标。

模块产出：为什么现在做 IP、90 天唯一主要目标、可观察成功标准、明确不追什么。「发 30 条」是动作，不是成功结果；「涨粉」若没有数量、质量或下一步行为，仍不可判定。

### 2. 证据 `evidence`

**首问：** 过去两年，别人最常拿哪一类具体问题来找你？

追问优先级：真实事件 → 当时做了什么 → 结果或对方反馈 → 能否合法、脱敏展示。

证据包括：职业经历、个人转变、可重复的方法、案例、作品、资质、长期被求助的问题。「我很热爱」和「我觉得自己擅长」只是自评，不是已验证能力。

用户说「我什么都不会」时，改问「过去一个月，有谁请你帮过什么，哪怕你觉得很小？」。仍无证据时，把「创作者能力边界」记为未知，不伪造专家身份。

模块产出：可提供的能力、一手经历、反复问题、可展示的信任依据、不可声称的边界。

### 3. 用户 `audience`

**首问：** 在你真正帮过或深度理解的人里，哪一类人的处境你一听就知道他为什么卡住？

追问要把人群压到「一人一阶段一问题」：

- 他处在什么阶段，空间、时间、金钱或身份约束是什么？
- 他刚刚发生了什么，为什么会在此刻点开这条内容？
- 他试过什么，为什么没成？
- 哪类人不服务？错误流量会长什么样？

用户有能力但不知道服务谁时，根据「他已解决过的问题 × 能触达的人 × 90 天目标」提出 2—3 个候选人群，并说明每个的证据强弱、变现距离和错误流量风险。

模块产出：目标用户的具体状态、核心问题、失败尝试、不服务谁。

### 4. 价值 `value`

**首问：** 这类人看完你的一条内容，当下最应该多出哪一个具体收获？

分清两层：

- **当前价值**：这一条当下帮他解决什么、看见什么或完成什么。
- **未来价值**：连续关注 30—90 天，他预期稳定得到什么。

再判定主价值类型是工具、情绪还是身份。不要为凑表把三种都写成主价值；明确商业转化的账号要检查工具落点，人物、故事、陪伴或审美型账号可以以情绪或身份为主。

模块产出：当前价值、未来价值、主价值类型、能持续供给的东西。

### 5. 商业与行为 `business`

**首问：** 未来 90 天，你最希望对的观众看完后主要做哪一个行为？

主行为一次只选一个：关注、搜索、私信、预约、试用、进店、购买或另一个可观察行为。「点赞评论转发关注」不是一个主行为。

继续问当前变现锚点、未来变现方向或不直接变现的长期用途。若有明确产品或服务，从真实成交或使用场景倒推人群，不先追大流量。明确「错误流量」：哪类人来了会高播放但不会进入长期用途，甚至会稀释定位。

模块产出：当前主行为、当前/未来变现方向或长期用途、错误流量定义。

### 6. 执行与红线 `execution`

**首问：** 按你现在的真实生活，每周能稳定拿出多少时间和哪些现成资源？

追问只围绕可执行性：擅长讲述还是呈现，能稳定保持的频率是多少，最常在哪一环卡住，哪些个人/客户/公司信息不能公开，哪些资质、疗效、收益、投资、法律或安全表述不能越界，哪种对外姿态不是他。

平台、内容类型、表达风格、内容支柱、账号记忆资产和更新频率可作暂定假设；不必等它们全部确定才行动。

模块产出：每周执行资源、适合形式、暂定稳定频率、真实卡点、人设/伦理/隐私/合规红线。

## 四、自适应追问法

不按固定题序机械读问卷。每次回答后做三步：

1. **抽事实**：只保留用户真正说过的经历、行为、结果和约束。
2. **找决策缺口**：问「下一个未知中，哪一个会改变目标、人群或价值的取舍？」
3. **只问这一个**：问题必须能引出一个事件、一个二选一、一个可观察标准或一个约束。

四种常见回答的处理：

- **空洞词**（「帮助普通人」）：要一个最近真实人物与当时场景。
- **自我评价**（「我挺会沟通」）：要一次被请来解决问题的过程与结果。
- **多目标并列**：要一个 90 天主目标，其它降为次级结果或明确不追。
- **完全答不出**：引用已知事实，提 2—3 个可选方向；给出 agent 的推荐与理由，但把未经证据支持的部分标为假设。

## 五、模块小结与纠偏

每完成一个模块，用以下四行小结：

```markdown
我当前的理解：……
我看到的取舍/矛盾：……
还不知道：……
如果上面没偏，下一个我只问：……
```

用户纠偏后，以用户新确认为准，但保留「为什么改」的依据。小结不是为了展示 agent 聊了很多，而是防止用户的话被 agent 过度解读。

## 六、首次建档完成门槛

以下字段必须有可作决策的内容，才能从 `in_progress` 进入 `provisional`：

1. 为什么现在做 IP。
2. 90 天唯一主要目标。
3. 成功标准。
4. 目标用户的具体状态。
5. 用户的核心问题。
6. 凭什么由这个创作者解决（信任依据或明确证据缺口）。
7. 当前价值与未来价值。
8. 当前主行为。
9. 变现方向或长期用途。
10. 每周执行资源。
11. 人设/伦理/隐私红线。
12. 当前最大未知。

「未知」可以是合法值，但必须写明未知的是什么以及怎么验证，不能用「待定」两个字冒充完整。

可暂定为假设：平台、内容类型、表达风格、内容支柱、账号记忆资产、更新频率。

首次问答不能强行确定：真正跑得动的系列、稳定记忆资产、哪类选题持续转粉、用户最终为何关注、观众对创作者的稳定认知。这些一律进入数据和契约验证。

## 七、v0.1 建档草案输出格式

六模块达到门槛后，先完整展示草案，不边展示边零碎写成正式档案：

```markdown
# v0.1 暂定档案草案

## 一、当前决策
- 为什么现在做 IP：
- 90 天唯一主要目标：
- 成功标准：
- 明确不追：
- 目标用户具体状态：
- 用户核心问题：
- 信任依据：
- 当前价值 / 未来价值：
- 当前主行为：
- 变现方向或长期用途：
- 执行资源：
- 红线：
- 当前最大未知：

## 二、依据账本
| 结论 | 状态（已确认事实/暂定假设/未知） | 依据 | 下一步验证 |
|---|---|---|---|
|  |  |  |  |

## 三、首批验证
- 最小可执行假设：
- 第一批只验证：
- 不在首批宣布为定论的内容：
```

用户看过完整草案后，一次无歧义确认即可原子写入 `ip-dossier.md`，设为 `onboarding_status: provisional`。不要重复确认，不得代用户确认。

依据账本「状态」列只能写 `已确认事实`、`暂定假设` 或 `未知`。例如“稳定定位已经成立”不能写成第四状态“现在不能宣布”；应改写为“稳定定位是否成立｜未知｜尚无数据｜用首批内容验证”。后续复盘里的 `已验证 / 待验证 / 已证伪` 是另一套认知状态，不混进首次建档账本。

## 八、已有档案与换定位

- **`confirmed` 且核心字段齐全**：跳过完整建档访谈，直接根据用户当前任务进入诊/契/行/盘。
- **`provisional` 且核心字段齐全**：不重跑六模块；优先执行首批验证，遇到影响当前任务的未知才补问。
- **核心字段缺失**：只问会影响当前决策的缺口；不从 `goal` 重头走一遍。
- **用户主动换定位**：先写明什么变了、为什么变、哪些已确认事实仍保留；只重跑受影响的模块，并在「底座修订留痕」写日期、旧结论、新假设、修订依据和验证方式。

## 九、模式 B 三问微诊断

模式 B 不强制完整建档。用户目标明确时直接交付；用户直接要内容、但下列任一项明显不清时，最多做三问微诊断，仍然一次只问一个：

1. 给谁看？
2. 希望看完做什么？
3. 凭什么由你讲？

三问后仍不清楚，可基于显式假设产出「探索稿」：必须在产出前列出「已知事实 / 本稿假设 / 最大未知」，并标明「这不是精准定稿」。用户已明确拒绝建档时，不再劝建档；微诊断只为不制造方向错的内容。

## 十、反模式

- **复制空模板就放行**：文件存在不等于档案完整。
- **二十问连珠炮**：用户会给出最短、最空、最没证据的答案。
- **直问定位与目标用户**：把本应由 agent 诊断的工作退回用户。
- **把空话升级为事实**：不得把「想涨粉、帮助普通人、真诚分享」直接写成正式定位。
- **用假设填满档案却不标记**：不写依据和验证方式的假设，很快会被当成事实。
- **为了完美无限追问**：有了最低可执行假设就进首批验证。
- **第一次聊天就宣布系列、记忆资产或转粉规律已成立**：这些只能由后续数据形成。
- **不记断点**：中断后重问全部问题，等于没有跨会话陪跑。
